# v0.3 Step 6B — Alertmanager foundation

## Architecture

The [Step 6A metrics](v0.3-observability-foundation.md) feed this local flow:

```text
API /metrics/ → Prometheus rules → Alertmanager → orbitalai-local
                      ↓                         (no delivery integration)
                Grafana ALERTS panel
```

Prometheus keeps its `orbitalai-api` job, 15-second scrape/evaluation intervals
and existing version. It loads `observability/prometheus/rules/orbitalai-alerts.yml`
through a read-only mount and sends alerts to `alertmanager:9093` over
`orbitalai-observability`. The `orbitalai-alertmanager` job also scrapes that
service's `/metrics`; no new application collector is needed.

Alertmanager is pinned to **`prom/alertmanager:v0.34.0`**
([official release](https://github.com/prometheus/alertmanager/releases/tag/v0.34.0)).
The host endpoint is **`127.0.0.1:9093`**. Configuration is mounted read-only from
`observability/alertmanager/alertmanager.yml`; the `orbitalai-alertmanager` volume
stores its silence/notification state. Cluster gossip is disabled for this
single-node deployment. No notification credentials or external transports exist.

These are **operational/platform alerts**, not collision-risk assessments.
No covariance/Pc exists. Conjunction physics remains deterministic and unchanged;
AI is not involved. No object, pair, event or exception-text labels are introduced.

## Rules and initial thresholds

All rules have `severity`, `component`, `summary` and `description`.
Critical means an unavailable dependency or failed screening execution; warning
means degraded inputs/coverage, provider execution failure or a recent partial
screening failure. These levels do not express orbital risk.

| Alert | Severity / component | Condition | Hold (`for`) |
| --- | --- | --- | --- |
| `OrbitalAIApiDown` | critical / api | `up{job="orbitalai-api"} == 0` | 2m |
| `OrbitalAIPostgresNotReady` | critical / postgres | Existing readiness gauge is 0, API is UP, readiness check age <120s | 2m |
| `OrbitalAIConjunctionScreeningFailure` | critical / conjunction | `conjunction_failures_total` increases within 15m | 1m |
| `OrbitalAIPropagationFailures` | warning / conjunction | Latest completed run has grid propagation failures; completion age is 0–15m | 1m |
| `OrbitalAIRefinementFailures` | warning / conjunction | Latest completed run has refinement failures; completion age is 0–15m | 1m |
| `OrbitalAISpaceTrackIngestionStale` | warning / ingestion | Observed successful sync is >2h old | 5m |
| `OrbitalAICelesTrakIngestionStale` | warning / ingestion | Observed successful sync is >4h old | 5m |
| `OrbitalAISatcatIngestionStale` | warning / ingestion | Observed successful sync is >24h old | 5m |
| `OrbitalAIIngestionFailure` | warning / ingestion | `ingestion_failures_total` increases within 15m | 1m |
| `OrbitalAIEphemerisCoverageDegraded` | warning / ephemeris | Screening-eligible / Earth-orbit objects <0.75, with a nonzero denominator | 15m |

Metric names in the table omit the shared `orbitalai_` prefix where abbreviated;
the rule file uses the exact Step 6A names. Four groups cover platform,
conjunction, ingestion and ephemeris. Provider/source labels retain Step 6A's
three/four bounded values; Prometheus job/instance identify the fixed targets.

Provider thresholds are initially **2× cache TTL** (1h, 2h, 12h). Cache TTLs do
not schedule ingestion: tune these thresholds to the actual operator cadence.
Zero/absent success timestamps stay quiet; there is no "never synced" alert.
The 75% coverage threshold is an initial operational baseline, subject to tuning.

Staleness, coverage and latest-run warnings require their collector to be
available and the API to be UP, so retained snapshots do not produce current
outage claims. Latest-run failures expire at a completion age of 15m, regardless
of the screened orbital time window. PostgreSQL uses the existing 15-second
Docker readiness probe; scraping adds no active database check.

## Routing, grouping and Grafana

The root route terminates in **`orbitalai-local`**, which deliberately has no
notification integration. Alertmanager's API/UI still exposes alert and routing
state. External receivers can later be attached here without changing the rules.

Grouping uses `[alertname, severity, component]`, with `group_wait: 30s`,
`group_interval: 5m`, `repeat_interval: 4h`; `resolve_timeout` is 5m when an alert
does not supply its own end time. A critical alert inhibits a warning only when
`alertname`, `component`, `provider` and `source` match. This avoids suppressing
another provider/source. Each current rule has one fixed severity; the inhibition
also supports future escalation and is exercised by the synthetic smoke test.

The existing provisioned dashboard gains one **Firing Alerts** stat (17 panels):
`sum(ALERTS{alertstate="firing",alertname=~"OrbitalAI.*"}) or vector(0)`.
The previous 16 panels are unchanged. Direct Alertmanager API injections do not
create Prometheus `ALERTS` series and therefore do not increment this panel.

## Validation commands

Run from the repository root in Bash; tools run inside the pinned containers:

```bash
promtool_local() {
  docker run --rm --entrypoint promtool \
    -v "$PWD/observability/prometheus:/etc/prometheus:ro" \
    -v "$PWD:/workspace:ro" -w /workspace/tests/observability \
    prom/prometheus:v3.14.0 "$@"
}
promtool_local check config /etc/prometheus/prometheus.yml
promtool_local check rules /etc/prometheus/rules/orbitalai-alerts.yml
promtool_local test rules orbitalai-alerts.test.yml

amtool_local() {
  docker run --rm --entrypoint amtool \
    -v "$PWD/observability/alertmanager/alertmanager.yml:/etc/alertmanager/alertmanager.yml:ro" \
    prom/alertmanager:v0.34.0 "$@"
}
amtool_local check-config /etc/alertmanager/alertmanager.yml
amtool_local config routes test \
  --config.file=/etc/alertmanager/alertmanager.yml \
  --verify.receivers=orbitalai-local \
  alertname=OrbitalAIAlertingSmokeTest severity=warning component=observability

.venv/bin/python -m pytest -q tests/test_observability.py -k dashboard
orbital_compose=(docker compose --env-file .env \
  -f deploy/compose/compose.core.yml -f deploy/compose/compose.observability.yml)
"${orbital_compose[@]}" config --quiet
"${orbital_compose[@]}" up -d --no-deps alertmanager prometheus
curl --fail http://127.0.0.1:9090/-/ready
curl --fail http://127.0.0.1:9093/-/ready
curl --fail http://127.0.0.1:9090/api/v1/alertmanagers
curl --fail http://127.0.0.1:9090/api/v1/targets
curl --fail 'http://127.0.0.1:9090/api/v1/rules?type=alert'
```

### Safe smoke procedure

1. Ensure no `OrbitalAIAlertingSmokeTest` alerts already exist. POST a JSON array
   to `http://127.0.0.1:9093/api/v2/alerts` with labels `alertname` set to that
   name, `severity=warning`, `component=observability`, an explicit UTC `startsAt`
   and `endsAt` two minutes in the future. Finite expiry bounds an interrupted test.
2. GET `/api/v2/alerts` and `/api/v2/alerts/groups`, filtered by
   `alertname="OrbitalAIAlertingSmokeTest"`. Verify the active alert, grouping
   labels and receiver `orbitalai-local`.
3. Optionally inject the same labels with `severity=critical`. Verify the warning's
   `status.inhibitedBy` contains the critical alert's fingerprint and two severity
   groups use the local receiver.
4. In a `finally` cleanup, POST each synthetic alert with the same labels and an
   `endsAt` in the past (after `startsAt`); poll until no active smoke alerts remain.

This verifies local ingestion/routing/inhibition, alongside rule unit tests and
Prometheus discovery/reachability. It does not exercise external delivery or a
live failure-triggered Prometheus notification. No permanent firing rule or
deliberate API/database outage is required.

## Limits and next integration point

- Collectors refresh lazily every 60s; scrape visibility normally takes up to
  75s, followed by rule evaluation and hold/grouping delays.
- `increase()` needs multiple observations. Pre-existing failures at the first
  scrape, hard process kills/OOM or failed telemetry writes can go unobserved.
  These rules do not detect worker liveness or replace the persisted run record.
- No first-sync or collector-unavailable alert is added; guarded rules can stay
  quiet when those observations are missing. Runtime provider success timestamps
  were still unobserved; provider conditions were validated with synthetic series.
- Local receiver state is the completion point for Step 6B. Configure approved
  external transports later; logging infrastructure belongs to Step 6C.
