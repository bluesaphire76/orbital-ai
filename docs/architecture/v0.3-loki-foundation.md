# v0.3 Step 6C — Loki logging foundation

## Purpose

Step 6C adds centralized local logging to OrbitalAI without changing orbital mechanics, ingestion semantics, or conjunction calculations.

The logging pipeline is:

```text
Docker stdout/stderr
        |
        v
Grafana Alloy
        |
        v
Grafana Loki
        |
        v
Grafana
```

## Components

- Grafana Loki 3.7.6
- Grafana Alloy 1.19.2
- Grafana 13.2.1
- Prometheus 3.14.0

Loki runs as a single local monolithic instance using filesystem storage.

Alloy discovers OrbitalAI Docker containers through the local Docker socket and forwards their stdout/stderr to Loki.

## Loki storage and retention

Loki uses:

- TSDB
- schema v13
- filesystem chunks
- filesystem index/storage
- Loki Compactor retention

Retention is configured to:

```text
168h
```

which corresponds to seven days.

No external object store or cloud logging service is used.

Anonymous Loki usage reporting is disabled.

## Log labels

Only two bounded labels are deliberately indexed:

- `platform=orbitalai`
- `service_name=<docker-compose service>`

The runtime validation confirmed that these are the indexed Loki labels.

The following are deliberately not indexed:

- container ID
- container name
- worker run ID
- NORAD catalog ID
- orbital object ID
- conjunction event ID
- conjunction pair ID
- exception text

This avoids high-cardinality Loki streams.

## Docker discovery

Grafana Alloy uses Docker service discovery through:

```text
/var/run/docker.sock
```

Only containers belonging to the Docker Compose project:

```text
orbitalai
```

are retained by the relabel pipeline.

The Compose service label becomes:

```text
service_name
```

and the static platform label is:

```text
platform=orbitalai
```

## Worker logs

Conjunction and ingestion jobs currently execute from the OrbitalAI API image.

One-shot Docker Compose containers launched through the `api` service therefore appear in Loki with:

```text
platform="orbitalai"
service_name="api"
```

Step 6C intentionally does not redesign application logging to introduce a separate worker/component field.

That can be added later if operational evidence shows a need to separate API, ingestion, and conjunction messages without relying on message contents.

## Grafana

A provisioned Loki datasource is available with UID:

```text
orbitalai-loki
```

and URL:

```text
http://loki:3100
```

The provisioned dashboard is:

```text
OrbitalAI - Platform Logs
```

It provides views for:

- all OrbitalAI logs
- API / worker logs
- observability stack logs
- errors and warnings

Prometheus remains the default Grafana datasource.

## Prometheus integration

Prometheus additionally scrapes:

The existing Step 6B Alertmanager rules remain unchanged.

## Security

All externally exposed observability ports remain bound to localhost.

Alloy requires read access to:

```text
/var/run/docker.sock
```

for Docker discovery.

Docker socket access is privileged and must remain restricted to the trusted local observability collector.

No application credentials are stored in Loki labels or observability configuration.

## Scope boundaries

Step 6C does not introduce:

- host journal collection
- Windows Event Log collection
- cloud log shipping
- OpenTelemetry tracing
- Grafana Tempo
- distributed Loki
- external Loki storage
- application structured-logging redesign
- log-derived orbital risk calculations
- log-derived conjunction assessment
- AI-based log analysis

Orbital calculations remain deterministic and unchanged.
