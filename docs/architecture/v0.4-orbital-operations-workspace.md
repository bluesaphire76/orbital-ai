# OrbitalAI v0.4 — Orbital Operations Workspace

## 1. Objective and architecture

The v0.4 Orbital Operations Workspace turns the initial OrbitalAI
visualization foundation into an operational 3D workspace for catalog,
object and conjunction analysis.

The primary interface is a CesiumJS-based orbital mission-control view:

- left-side catalog search and object operations;
- central interactive 3D Earth;
- contextual active-object and conjunction information;
- targeted playback controls;
- conjunction analysis and exact-event replay.

The browser is visualization-only for orbital mechanics.

Authoritative orbital propagation remains in the backend:

```text
Catalog / OMM / GP sources
          |
          v
Canonical ephemeris selection
          |
          v
Deterministic SGP4 propagation
          |
          +----> Visualization snapshots
          |
          +----> Targeted playback
          |
          +----> Conjunction screening
```

Cesium interpolates deterministic backend-generated samples but does
not calculate authoritative trajectories, TCA, miss distance or
collision probability.

### Selection model

The Cesium globe remains the authoritative owner of interactive
selection state:

- selected object IDs;
- active object ID;
- camera lock state.

Selection is exposed to surrounding UI through event bridges rather
than moving globe authority into React context.

This avoids selection races between Cesium interaction and React
component lifecycle.

### Canonical visualization catalog

Visualization snapshots now use the same canonical ephemeris selection
logic as conjunction screening instead of being restricted to one
provider.

This keeps the globe and deterministic analysis aligned on the same
orbital data policy.

### Object visualization semantics

Object colors represent object classification rather than ephemeris
freshness:

- `PAYLOAD` — cyan;
- `DEBRIS` — orange;
- `ROCKET_BODY` — yellow;
- `UNKNOWN / OTHER` — neutral white.

The object legend is collapsible and rendered independently from the
active-target inspector.

### Earth rendering

High-resolution mode uses Cesium World Imagery and World Terrain.

Solar illumination is derived from the Cesium clock, preserving visual
consistency with playback and conjunction TCA.

Night-time city lights are rendered using a separate unlit emissive
shell with a local NASA Black Marble 3 km texture.

The shell applies its own Sun-direction mask and does not participate
in Cesium globe vertex lighting. This prevents city-light emission from
being darkened with the terrain on the night hemisphere.

The experimental NASA Black Marble 500 m tiled/LOD implementation was
explicitly rejected after regression testing. The stable 3 km local
texture remains the v0.4 implementation.

## 2. Dependencies and integrations

### Frontend

- Next.js 16
- React 19
- TypeScript
- CesiumJS
- local NASA Black Marble 2016 3 km raster asset

Cesium ion is used for high-resolution World Imagery / World Terrain.

The city-light texture itself is stored locally.

### Backend

- FastAPI
- SQLAlchemy
- PostgreSQL
- deterministic SGP4 / orbital-engine services

### Data sources

The visualization layer consumes orbital elements already normalized
and stored by OrbitalAI.

Canonical selection can use available ephemerides from:

- Space-Track;
- CelesTrak.

SATCAT provides catalog metadata and classification.

### Observability

Existing Prometheus, Grafana and Loki foundations remain external to
the visualization path and must not block rendering or orbital
calculation.

## 3. Key logical choices

### Backend remains authoritative

Trajectory calculation, propagation and conjunction analysis remain
server-side.

This prevents browser-specific numerical behavior from influencing
operational results.

### Targeted playback only

OrbitalAI does not implement global catalog playback.

Playback is materialized only for:

- selected objects;
- conjunction pairs.

This bounds backend propagation work and browser entity load.

### Exact conjunction replay

Conjunction events retain the exact primary and secondary orbital
element identifiers used during screening.

Replay therefore reconstructs the event from the same elements rather
than selecting the newest elements available at replay time.

### Canonical ephemeris selection

The globe no longer assumes CelesTrak is the sole visualization source.

The same canonical source-selection policy used by analysis is reused
for visualization.

### Local city-light rendering

City lights are deliberately not implemented as a normal Cesium
`ImageryLayer`.

World Terrain vertex lighting is applied after imagery composition and
would darken the city-light overlay on the night hemisphere.

The unlit emissive shell isolates artificial light emission from terrain
lighting while preserving the actual Cesium Sun direction.

## 4. Maintenance and points of attention

### Orbital source policy

Changes to provider priority or freshness rules must be made in the
canonical ephemeris-selection layer, not independently in the globe.

Current freshness policy:

- warning: 12 hours;
- stale: 24 hours;
- maximum accepted age: 72 hours.

### Playback

When modifying targeted playback, preserve:

- backend-generated deterministic samples;
- exact conjunction element IDs;
- maximum object safety limits;
- temporary materialization for objects absent from the current
  visualization snapshot.

Do not reintroduce browser-side authoritative propagation.

### Globe selection

Do not move active-object ownership out of `OrbitalGlobe` without
revalidating Cesium/React event ordering.

The previous context-owned selection experiment caused regressions and
was rolled back.

### Earth lighting

The current Cesium solar-lighting parameters and emissive city-light
shell are a validated baseline.

Avoid changing terrain lighting while modifying city lights.

The NASA Black Marble 500 m tiled/LOD experiment is intentionally out
of scope for v0.4 after rendering regressions.

### Catalog scale

Rendering and search must remain safe at approximately 30k active
canonical objects.

Any future visual additions should avoid one expensive React component
per orbital object.

### Catalog synchronization hardening

Automated catalog and ephemeris synchronization is implemented on the
v0.4F.1 feature branch:

- SATCAT metadata synchronization;
- CelesTrak fallback synchronization;
- Space-Track primary ephemeris synchronization;
- scheduling;
- persistent sync state;
- Prometheus metrics;
- API status endpoint;
- freshness visibility.

Its architecture, operations, API, metrics and limits are documented in
[v0.4F.1 — Automated Catalog & Ephemeris Synchronization](v0.4f1-automated-catalog-ephemeris-synchronization.md).
