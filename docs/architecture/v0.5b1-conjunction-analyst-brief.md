# v0.5B.1 Conjunction Analyst Brief Backend

## Status and scope

This document describes development work and does not declare v0.5 released.
The backend can generate one explanatory brief for one already persisted
conjunction event. It adds no frontend, automatic generation, streaming, chat,
cache, brief history, database table, or migration.

## Trust boundary

PostgreSQL and the deterministic conjunction engine remain authoritative for
the event, run, element provenance, TCA, miss distance, and relative velocity.
The model explains those persisted facts. It does not propagate an orbit,
select ephemerides, calculate collision probability, assign risk or severity,
recommend a maneuver, or update data. Human review is mandatory for operational
decisions.

```text
persisted event + exact run/object/element rows
                    |
                    v
       immutable full grounding context
                    |
                    v
       minimal model-only projection
                    |
                    v
       shared bounded AI gateway -> local llama.cpp
                    |
                    v
 strict post-validation + deterministic facts response
```

## Endpoint

`POST /ai/conjunctions/{event_id}/brief` accepts one positive integer path
parameter. The route rejects any request body and any query parameter. It does
not accept user messages, prompts, temperature, token limits, model/provider
selection, or system instructions.

Every valid request performs one generation. v0.5B.1 intentionally has no
persistent or in-memory result cache.

## Exact event replay and grounding

One repository query joins the requested `ConjunctionEvent` to its persisted
`ConjunctionRun`, primary and secondary `OrbitalObject`, and the two
`OrbitalElement` rows referenced by `primary_element_id` and
`secondary_element_id`. It never calls canonical ephemeris selection, chooses
newer elements, propagates state, or contacts an orbital-data provider.

The frozen `ConjunctionBriefContext` contains:

- event and run IDs, run source, start/completion time, and window bounds;
- each object database ID, NORAD catalog ID, name, optional international
  designator, and optional object type;
- each exact element ID, source, and epoch;
- persisted TCA, miss distance in kilometres, relative velocity in kilometres
  per second, and refinement method.

Grounding fails closed unless the run source is `canonical`, both objects are
distinct, every ID relationship is consistent, each element belongs to the
corresponding object, the TCA lies in the run window, IDs are positive, numeric
facts are finite and non-negative, and every timestamp is timezone-aware.

Times are normalized to UTC ISO 8601. Text is Unicode-normalized, stripped of
control characters and whitespace-normalized, then bounded to the database
field size. Optional fields alone may be null. Object names and designations
remain in the full context used for the response, hash, audit, and exact replay.
They are not included in the model projection.

The context is serialized with sorted keys, compact separators, ASCII-safe
escaping, and forbidden NaN values. The response exposes the SHA-256 of these
canonical bytes for reproducibility.

The separate frozen `ConjunctionBriefModelContext` contains only primary and
secondary roles, optional object types, element sources and epochs, persisted
TCA, miss distance, relative velocity, screening method, run window, and run
completion time. It contains no event, run, object, NORAD, or element IDs and
no names or designations. Exact element IDs remain verified and returned as
deterministic facts without being exposed to the model.

## Prompt and structured output

The fixed prompt version is `conjunction-analyst-brief-v2`; neither the prompt
nor provider configuration is returned. The task label is the bounded
`conjunction_analyst_brief` enum value. Qwen reasoning remains disabled through
the provider's `reasoning_effort=none` and `enable_thinking=false` settings.

The provider receives a strict JSON Schema with no additional properties. It
requires a 20–320 character executive summary, one to three evidence-backed
observations of 15–180 characters, one to three allowlisted checks, and one to
three allowlisted limitations. Each observation cites one to three evidence
fields. A pure function builds the evidence enum from fields actually present,
non-null, finite where numeric, and included in the model projection. The
provider therefore cannot select unavailable evidence through the schema.

The prompt requests a short summary, at most two observations during normal
generation, simple sentences, no repetition, and an immediately closed JSON
object. The output limit is 384 tokens. The prompt uses positive operational
language focused on monitoring, verification, and human review while retaining
the prohibition on orbital calculations and operational decisions. Narrative
text may contain no ASCII or Unicode numeric characters.

## Post-generation controls

Provider schema enforcement is only the first boundary. The backend parses the
entire response as JSON and validates it again with strict Pydantic models. It
rejects extra fields, invalid lengths or counts, empty strings, duplicated
items, non-allowlisted checks or limitations, unknown evidence, and evidence
whose actual context value is null. Each observation must cite evidence.

The response is also rejected if it contains reasoning content, thinking tags,
Markdown fences, surrounding text, a non-`stop` finish reason, digits in the
executive summary or observation text, a prescriptive maneuver instruction, an
invented collision probability, or an explicit new risk or severity
classification. Neutral language such as monitoring the next screening,
verifying ephemeris freshness, and requiring human review remains valid.
Narrative must refer to “primary object” and “secondary object”. Validation
failure causes no automatic retry.

The three enum arrays—`recommended_checks`, `limitations`, and each
`evidence_fields` list—represent bounded sets. llama.cpp can emit an identical
enum more than once even though the provider schema retains
`uniqueItems=true`. Before strict Pydantic validation, the backend makes a deep
copy of the decoded JSON and removes only repeated, exactly identical, known
enum strings from those three locations. It preserves the first occurrence and
its order, then applies all minimum and maximum item bounds to the canonical
copy.

Canonicalization does not add or replace values, correct spelling, fold case,
coerce types, remove unknown enum values, merge observations, or rewrite
narrative or numeric content. Missing fields, unknown values, wrong types,
empty arrays, repeated observations, invalid narrative, and every semantic
violation therefore remain fail-closed. Each changed enum set emits a bounded
`conjunction_brief_output_normalized` record containing only the task,
normalization code, removed count, and timestamp. Normalization codes are not
Prometheus labels.

Every validation rejection has one bounded internal reason code:
`output_truncated`, `invalid_json`, `schema_invalid`,
`finish_reason_invalid`, `reasoning_present`, `thinking_tag_present`,
`narrative_digit`, `unavailable_evidence`, `duplicate_evidence`,
`duplicate_item`, `maneuver_instruction`, `invented_probability`,
`invented_risk_classification`, `empty_content`, or
`unexpected_validation_error`. The structured warning contains only a fixed
event name, task, reason code, bounded field path and finish reason, token
counts, output SHA-256, and timestamp. It contains no raw output, prompt,
payload, object name, identifier, key, path, or URL. The public 502 response
remains generic.

## Response boundary

HTTP 200 separates:

- deterministic `event` facts from PostgreSQL;
- the validated AI `brief`;
- bounded metadata: task, prompt version, grounding hash, UTC generation time,
  public provider/model aliases, finish reason, tokens, and duration;
- a fixed disclaimer requiring human review.

It never exposes API keys, provider URLs, model paths, image digests, prompts,
raw provider responses, stack traces, or local filesystem paths.

## Failure modes

| Status | Condition |
|---:|---|
| 404 | Event does not exist |
| 409 | Persisted grounding is incomplete or inconsistent |
| 429 | Bounded gateway queue is full |
| 502 | Provider output fails parsing or post-validation |
| 503 | Local AI is disabled or the provider is unavailable |
| 504 | Provider/gateway timeout |

Mapped messages are bounded and do not contain upstream response bodies. The
gateway performs no automatic retry. Global API health and deterministic v0.4
services remain independent of AI failure.

## Queue, metrics, and Grafana

The endpoint uses the application-owned `AIGateway`, its shared semaphore,
bounded waiting queue, timeout, provider, and token accounting. Generation
success is recorded only after post-validation. Provider transport failure
marks availability unavailable; a valid generation restores it.

Prometheus uses the existing AI metric families. The only task label added is
`conjunction_analyst_brief`; outcomes are a fixed allowlist including
`grounding_error` and `validation_error`. Validation reason codes are not metric
labels. No event, run, object, model path, error, hash, or request ID appears in
a label.

The existing **Orbital Operations Overview** dashboard adds a **Local AI** row
with provider availability, requests by task/outcome, request duration, prompt
and completion tokens, active/queued requests, and errors/rejections. Existing
dashboard UID, panel IDs, queries, datasources, and layout remain intact.

## Runtime validation

Runtime validation selects one event read-only from the latest completed
canonical run using a deterministic ordering. Before generation it verifies
that screening is idle, llama.cpp is healthy, the CUDA log validator passes,
and baseline container IDs, restart counts, and AI metrics are recorded. Only
the API image is rebuilt with `--no-deps`; llama.cpp and schedulers are not
restarted.

At most two model generations may be used for runtime validation. A successful
first POST ends inference. A 502 may lead to one final POST only after its
bounded reason code identifies a concrete defect, that defect receives a
focused regression test, and the API alone is rebuilt. Infrastructure failures
are diagnosed separately and do not justify schema changes or request loops.

One successful POST must prove exact element IDs, grounding hash, schema and
evidence validity, digit-free and non-thinking narrative, disclaimer, tokens,
latency, metric increments, and queue/active return to zero. No screening is
started and no event is modified.

The read-only validation used event `425179` from canonical Run `29`. Its exact
persisted element IDs remained `1095613` and `1097501`. The preflight proved an
idle screening scheduler, a ready provider, and full CUDA offload of 37/37
layers on the NVIDIA GeForce RTX 4070 Laptop GPU.

Exactly two new model generations were made. The first completed with provider
finish reason `stop` and 203 completion tokens, then post-validation returned

recorded. A focused prompt regression made narrative qualitative and directed
the model to cite values through `evidence_fields`; all dedicated, correlated,

The second and final generation completed with provider finish reason `stop`
and 208 completion tokens. Post-validation returned HTTP 502 with bounded
reason `duplicate_item` at `limitations`. No third request was made. The API,
provider, schedulers, Prometheus, and Grafana remained running with zero
restarts; AI active requests and queue depth returned to zero and provider
readiness remained one. This runtime result is **NO-GO** for commit and for
v0.5B.2 because no valid HTTP 200 brief has yet been demonstrated.

## Limits and deferred work

The brief is an explanation of one persisted snapshot. A later screening can
supersede that snapshot, and element age still requires analyst review. The AI
has no covariance or collision probability input. v0.5B.2 may add an explicitly
designed cache; UI integration remains deferred. Neither is part of v0.5B.1.
