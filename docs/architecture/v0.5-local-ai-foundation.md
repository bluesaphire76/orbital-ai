# v0.5 Local AI Foundation

## Status and scope

This document describes the v0.5A development foundation. It does not mark
v0.5 as released. Local AI is disabled by default, and the normal core plus
observability Compose stack does not require llama.cpp.

This phase provides configuration, a provider boundary, a bounded generation
gateway, health and capability endpoints, metrics, and an explicit NVIDIA CUDA
Compose overlay. The v0.5B.1 development work builds the fixed-input
Conjunction Analyst Brief on this boundary; it does not add chat or a public
free-form prompt endpoint.

## Authority boundary

OrbitalAI's deterministic engine remains authoritative for propagation,
candidate generation, conjunction screening, numerical refinement, TCA, miss
distance, relative velocity, and future collision probability calculations.
The LLM receives only application-prepared tasks and may later explain or
summarize persisted deterministic results. Its output cannot update or replace
orbital mechanics results.

## NVIDIA-only inference policy

OrbitalAI supports AI inference only on an NVIDIA CUDA device. CPU inference,
partial model-layer offload, automatic CPU fallback, and alternate CPU
providers are unsupported. The CPU remains available for FastAPI,
orchestration, networking, tokenization, JSON parsing, metrics, and unavoidable
host-side runtime work. Every LLM model layer must execute on the GPU.

Enabling AI requires the explicit CUDA Compose overlay and a successful
container GPU gate. If CUDA is absent or the selected model and context do not
fit in VRAM, llama.cpp must fail closed. The general API, `/health`, and
PostgreSQL `/ready` remain independent from the optional AI runtime.

```text
PostgreSQL + deterministic orbital engine
                    |
                    | typed, application-owned task
                    v
            bounded AI gateway
                    |
                    | OpenAI-compatible chat request
                    v
        private local llama.cpp server
```

## Backend design

`AIConfig` is an immutable environment-backed configuration object cached by
the application. `AIProvider` isolates the rest of the backend from llama.cpp
JSON. The provider exposes typed `health()` and `chat_completion()` methods and
returns internal models for content, token usage, timings, and health.

`LlamaCppProvider` calls only:

- `GET /health`;
- `POST /v1/chat/completions`.

Generation requests disable model reasoning, disable streaming, apply the
configured output-token ceiling, and can carry an application-owned JSON
schema. The client performs no retries and creates and closes one `httpx`
client per call in this foundation phase.

The gateway accepts only task labels defined in code:

- `foundation_probe`;
- `conjunction_analyst_brief`.

The analyst brief route submits the latter task through the same shared gateway.
Its grounding and validation are documented in
[v0.5B.1 Conjunction Analyst Brief](v0.5b1-conjunction-analyst-brief.md).

## Queue, concurrency, and timeout

An `asyncio.Semaphore` limits active generations. Active slots and waiting
requests are counted separately under an asynchronous lock. A request is
rejected immediately when all execution slots and all configured waiting slots
are occupied. Cancellation and timeout paths release the semaphore and restore
both counters in `finally` blocks. Health checks bypass the generation queue.

Defaults are one active generation, 20 waiting requests, a 3-second connect
timeout, and a 45-second total/read timeout. These limits protect the API from
unbounded local inference load; they are not retries or workload scheduling.

## Public API

`GET /ai/capabilities` always returns HTTP 200 with the enabled state,
provider name, optional configured model alias, supported features, and bounded
limits.

`GET /ai/health` returns:

- HTTP 200 with `status=disabled` when AI is disabled;
- HTTP 200 with `status=ready` when llama.cpp is ready;
- HTTP 503 with `status=loading` while the model loads;
- HTTP 503 with `status=unavailable` for transport, malformed-response, or
  other provider failures.

Neither endpoint returns the base URL, API key, local model path, container
details, or upstream error bodies. AI health does not affect the global
`/health` or PostgreSQL `/ready` probes.

## Configuration

| Variable | Default | Purpose |
|---|---:|---|
| `ORBITAL_AI_ENABLED` | `false` | Enables the gateway configuration |
| `ORBITAL_AI_PROVIDER` | `llama.cpp` | Provider identifier; no other value is accepted |
| `ORBITAL_AI_BASE_URL` | `http://llama-server:8080` | Private HTTP(S) provider URL |
| `ORBITAL_AI_API_KEY` | empty | Required when enabled |
| `ORBITAL_AI_MODEL` | empty | Public model alias required when enabled |
| `ORBITAL_AI_CONNECT_TIMEOUT_SECONDS` | `3` | Connection timeout |
| `ORBITAL_AI_TIMEOUT_SECONDS` | `45` | Total/read and gateway timeout |
| `ORBITAL_AI_MAX_OUTPUT_TOKENS` | `512` | Output ceiling |
| `ORBITAL_AI_MAX_QUEUE` | `20` | Waiting request capacity |
| `ORBITAL_AI_CONCURRENCY` | `1` | Active generation limit |
| `ORBITAL_AI_TEMPERATURE` | `0.1` | Sampling temperature in `[0, 2]` |

Boolean parsing is strict (`true` or `false`). URLs must use HTTP or HTTPS and
cannot contain user information, query strings, or fragments. Positive limits
and finite positive timeouts are enforced at startup. The public model alias
cannot contain path separators. The API key is excluded
from dataclass representation, public responses, metrics, and mapped errors.

## Prometheus metrics

The API exports:

- `orbitalai_ai_runtime_ready`;
- `orbitalai_ai_requests_total{task,outcome}`;
- `orbitalai_ai_request_duration_seconds{task}`;
- `orbitalai_ai_queue_depth`;
- `orbitalai_ai_queue_capacity`;
- `orbitalai_ai_active_requests`;
- `orbitalai_ai_concurrency_capacity`;
- `orbitalai_ai_timeouts_total{task}`;
- `orbitalai_ai_prompt_tokens_total{task}`;
- `orbitalai_ai_completion_tokens_total{task}`.

Task and outcome labels use fixed allowlists. Models, prompts, object/event IDs,

Prometheus registry, including registries supplied to `create_app()` in tests.

## NVIDIA CUDA Compose runtime

`deploy/compose/compose.ai.cuda.yml` is the only supported AI runtime overlay.
The former CPU overlay was removed. The CUDA overlay extends the API and adds
`llama-server` on the internal `orbitalai-ai` network. It publishes no host
port, runs offline without its web UI, enables its API key and metrics, uses
`parallel=1`, uses a 4096-token context and 512 predicted tokens, and
mounts an existing local model directory read-only. The unconfigured model
path fails closed. Linux capabilities are dropped and `no-new-privileges` is
enabled. The server runs as the unprivileged host model-owner UID/GID
`1000:1000`, which can read the `0440` model without a DAC-bypass capability.
Restart attempts are bounded.

The llama.cpp API key is supplied through `LLAMA_API_KEY`, not as a process
argument, so routine process diagnostics do not expose it.

The image is exclusively
`ghcr.io/ggml-org/llama.cpp:server-cuda`, pinned to the validated linux/amd64
manifest digest
`sha256:98b8502c7d6f4f5221f44ba8606c8f61b049c176caae5746d4956115adad23e3`.
Its runtime command fixes:

- `--n-gpu-layers all`;
- `--device CUDA0`;
- `--split-mode none`;
- `--main-gpu 0`;
- `--fit off`;
- `--batch-size 512` and `--ubatch-size 128`;
- `--op-offload`, `--kv-offload`, and `--flash-attn on`;
- `--reasoning off`, in addition to the per-request structured
  `enable_thinking=false` template argument;
- no CPU MoE or feed-forward offload flags.

Compose reserves exactly one NVIDIA GPU. `llama-server --list-devices`
identified the single runtime device as `CUDA0: NVIDIA GeForce RTX 4070 Laptop
GPU`; the overlay passes that exact device to the server.

## GPU-only runtime evidence

`scripts/validate_llama_cuda_runtime.py` validates bounded startup-log evidence
without exposing it through a public API. It requires exactly one CUDA device,
the RTX 4070 Laptop identity, equal offloaded and total layer counts, and
positive CUDA model, KV-cache, and compute buffers. A positive CPU KV buffer is
rejected, as is a positive CPU compute buffer. The validator also requires a
server-ready log record. A CPU-mapped
model buffer alone is not treated as a CPU layer because
llama.cpp may report a memory-mapped file even when every layer is offloaded;
the explicit layer ratio remains authoritative.

The runtime is accepted only after a real model startup log passes:

```bash
docker compose \
  --env-file .env \
  -f deploy/compose/compose.core.yml \
  -f deploy/compose/compose.observability.yml \
  -f deploy/compose/compose.ai.cuda.yml \
  logs --no-color llama-server \
  | .venv/bin/python scripts/validate_llama_cuda_runtime.py
```

An HTTP `/health` response alone is insufficient evidence.

## Container GPU enablement

The development environment uses Docker Engine 29.8.1 directly inside Ubuntu
WSL2, not Docker Desktop. NVIDIA Container Toolkit 1.20.1 is installed from the
official stable repository. `/etc/docker/daemon.json` registers the `nvidia`
runtime while retaining `runc` as the default, so standard OrbitalAI services
do not acquire GPU access.

The gate ran the official NVIDIA `nbody` CUDA sample inside Docker. It detected
one RTX 4070 Laptop GPU with compute capability 8.9 and completed successfully.
Containerized `nvidia-smi` also reported the same GPU and 8188 MiB VRAM.

Docker Desktop and native Docker Engine require different procedures. Docker
Desktop uses its WSL2 GPU integration and its daemon must not be reconfigured
from the Linux distribution. Native Docker Engine requires NVIDIA Container
Toolkit plus `nvidia-ctk runtime configure --runtime=docker`. In both cases the
Windows NVIDIA driver is the only display driver: do not install a Linux
NVIDIA driver or alter `/usr/lib/wsl/lib`.

CUDA 12 is the initial llama.cpp runtime baseline. CUDA 13 is not validated,
even though the current Windows driver advertises CUDA 13.4 compatibility.

## Foundation probe and failure isolation

`scripts/probe_ai_gateway.py` is an internal, fixed-input validation command.
It accepts no user prompt. It sends the `foundation_probe` task through
`AIGateway` and `LlamaCppProvider` with a closed JSON Schema, a 256-token
ceiling, non-thinking mode, and no retries. It fails unless the response is
valid bounded JSON with `status=ok`, has finish reason `stop`, contains no
reasoning content or thinking tags, and leaves the semaphore and queue idle.
Its output includes bounded token, timing, and before/during/after metric
evidence.

Stopping `llama-server` must make only `/ai/health` unavailable. The platform
`/health`, PostgreSQL `/ready`, catalog worker, and conjunction scheduler remain
independent. Restart requires the same startup-log validator before AI health
can be accepted again.

If context 4096 cannot start with full offload or leaves less than 768 MiB free
VRAM after warmup, one explicit context-2048 retry is allowed. CPU fallback,
partial offload, `--fit on`, a second model, and repeated benchmarking remain
prohibited.

## Observed v0.5A.3 validation

The validation on 2026-09-21 used the pinned `server-cuda` linux/amd64 image
with image ID equal to its manifest digest,
`sha256:98b8502c7d6f4f5221f44ba8606c8f61b049c176caae5746d4956115adad23e3`.
The local image size was 6,989,389,788 bytes. Device discovery reported one
`CUDA0` device, the NVIDIA GeForce RTX 4070 Laptop GPU with compute capability
8.9.

The effective runtime configuration was context 4096, parallel 1, batch 512,
ubatch 128, Flash Attention enabled, 512 maximum gateway output tokens, and
thinking disabled at both server and structured request-template levels. The
runtime validator passed before and after failure isolation with:

- 37 of 37 layers offloaded to the GPU;
- 4,455.34 MiB CUDA model buffer;
- 576.00 MiB CUDA KV buffer;
- 25.00 MiB CUDA compute buffer;
- server ready, no OOM, no CPU KV cache, and no CPU compute backend.

llama.cpp also reported a 333.84 MiB read-only `CPU_Mapped` model view, a 0.58
MiB `CUDA_Host` output staging buffer, and a 5.00 MiB `CUDA_Host` compute
staging buffer. These are host mapping/orchestration allocations; the complete
37/37 layer ratio and CUDA model, KV, and compute buffers prove that model
execution did not fall back to the CPU.

VRAM was 663 MiB used and 7,286 MiB free before model loading. After startup
and warmup it was 5,869 MiB used and 2,080 MiB free. During the single gateway
probe it peaked at 5,878 MiB used with 2,071 MiB free and 100% GPU utilization.
The final idle state after the isolation restart was 5,866 MiB used and 2,083
MiB free, leaving 1,303 MiB above the required safety margin.

The integrity gate plus process startup took 7.514 seconds; the model-loading
portion took 1.654 seconds. The one fixed foundation probe returned
`{"status":"ok"}` with no reasoning content and finish reason `stop`. It used
51 prompt tokens and 29 completion tokens. Observed timings were 382.424 ms
prompt evaluation at 133.36 token/s, 915.029 ms generation at 30.60 token/s,
1,325.10 ms provider latency, and 1,326.84 ms total gateway latency.

The probe-local bounded metrics registry changed from zero to one successful
`foundation_probe`, recorded the same 51/29 tokens and 1.325-second request
duration, observed `active_requests=1` during execution, and returned active
requests and queue depth to zero. Native llama.cpp counters independently
reported the same token totals and 0.380574/0.915029 seconds. The API process
registry stays at zero for generation because the repeatable probe is a
separate internal process rather than a public API endpoint.

Host RAM remained healthy with more than 7.3 GiB available. Swap moved from
678 MiB after the naturally scheduled conjunction run to 952 MiB after the API
image build and probe, then stabilized at 957 MiB after the isolation restart.
Two one-second container-stat samples around the short probe observed 63.19%
CPU for the API-side orchestration process and 0% for llama.cpp; the 100% GPU
sample and llama.cpp timing counters captured the inference work. This CPU
sampling is coarse because the request completed in 1.33 seconds.

Failure isolation stopped only `llama-server`. AI health changed to HTTP 503
`unavailable`, while global health, PostgreSQL readiness, catalog status, and
the latest conjunction run stayed HTTP 200. API, catalog-sync, and
conjunction-screening retained their container IDs and zero restart counts.
Restarting only llama.cpp restored AI health and passed the runtime validator
again without a second generation. Conjunction Run 29 started naturally before
model loading and completed successfully with 81,475 events; no manual run was
started.

Startup uses the three Compose files and targets only the runtime:

```bash
docker compose \
  --env-file .env \
  -f deploy/compose/compose.core.yml \
  -f deploy/compose/compose.observability.yml \
  -f deploy/compose/compose.ai.cuda.yml \
  up -d --no-deps llama-server
```

After the log validator passes, `scripts/probe_ai_gateway.py` can be run inside
the API container. It performs exactly one fixed foundation request and accepts
no command-line prompt.

The first product task after foundation validation is the typed Conjunction
Analyst Brief, built from persisted deterministic conjunction data rather than
free-form user prompts.
