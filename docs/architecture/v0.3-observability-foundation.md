# v0.3 Step 6A — observability foundation

## Architecture and freshness

The API exposes Prometheus metrics at **`/metrics/`**. The existing `/metrics`
redirect is unchanged. Collectors reuse the `orbitalai_` namespace and existing
conjunction/propagation names; legacy duration-in-milliseconds gauges remain for
compatibility. New dashboards use seconds.

Each collector caches one complete snapshot for **60 seconds**, refreshed lazily
on a scrape. Registration does no I/O. Catalog coverage uses three SQL aggregate
queries over scalar columns, never a 30k-object ORM/OMM load. `MAX(epoch)` gives
the same age as canonical selection: its provider/id tie-breaks share that epoch.
No screening selection, physics, matching or lifecycle behavior is changed.

Refresh failures retain the last complete snapshot and set
`orbitalai_{conjunction,propagation,catalog,operations}_metrics_available` to zero.
Their corresponding `*_metrics_last_refresh_timestamp_seconds` identifies the
last successful refresh. With a 15-second scrape interval, changes normally
appear within **75 seconds**. Cached age gauges advance on refresh; use
`time() - ..._timestamp_seconds` for continuously advancing ages in dashboards.

One-shot workers run outside the API process. Their execution counters, timestamps
and histogram buckets therefore use a small shared JSON state in
`data/observability/operations.json`, on the existing Compose `/app/data` mount.
Updates use a POSIX file lock and atomic replacement. Storage has only four
screening-source and three ingestion-provider entries; it retains no run history,
object identifiers, exceptions, credentials or provider payloads. Metrics write
failures emit a generic warning and preserve the operation's return/exception.

Compose explicitly sets `ORBITAL_METRICS_DIR=/app/data/observability`. Host commands
default to `data/observability` relative to the repository root; they need access
to that same directory and compatible ownership. Prefer the existing Compose
worker commands. Runtime telemetry is ignored by Git and survives container
recreation. Removing this file resets cumulative counters and histogram history.

## Metric groups

| Group | Families and semantics |
| --- | --- |
| Latest screening | `orbitalai_conjunction_last_run_*`: objects, samples, chunks/width, grid propagation attempts/failures, expired skips, raw candidates, chunk-unique evaluations, refinements/failures, duplicates suppressed, events, max chunk workloads, duration and completion timestamp. Reads the most recently persisted run; includes historical runs. |
| Execution | `orbitalai_conjunction_runs_total{source}` counts finished executions, including failures; `..._failures_total` is the failed subset. `..._screening_duration_seconds` is a histogram of successful screening service durations, excluding persistence. Counters/histogram start when instrumentation is enabled; no historical backfill. |
| Catalog | `orbitalai_catalog_total_objects`, `..._earth_orbit_objects`, `..._objects_with_current_elements`, `..._canonical_elements_total`, `..._screening_eligible_objects`. Canonical coverage counts all objects with any latest element; eligibility counts Earth-orbit objects whose canonical elements are not expired **at refresh time**. The current-elements flag is not a freshness guarantee. |
| Ephemeris | `orbitalai_ephemeris_objects{status}` counts canonical **Earth-orbit** elements as fresh/aging/stale/expired, using the existing configured thresholds (inclusive at each boundary, future epochs fresh). Objects without elements are absent from this breakdown. |
| Ingestion | `orbitalai_ingestion_last_attempt_timestamp_seconds`, `..._last_success_timestamp_seconds`, `..._last_execution_duration_seconds`, `..._last_execution_success`, `..._runs_total`, `..._failures_total`, `..._records{provider,result}`. Service calls and CLI entrypoints are instrumented; nested calls count once and CLI duration includes fetch/application. Download exceptions are counted. |
| Health / legacy | `orbitalai_platform_info` and existing `orbitalai_propagation_*` metrics are retained. `orbitalai_database_ready` and `..._last_check_timestamp_seconds` reuse `/ready` checks, including Docker's existing probe. Prometheus `up{job="orbitalai-api"}` indicates scrape/API availability. No additional active probe runs inside `/metrics/`. |

Ingestion record gauges retain the **last successful** sync's counts. `received`
is input length for sized inputs, otherwise processed count; `matched` is processed
catalog objects (Space-Track excludes unmatched objects); `imported` means new
SATCAT objects or newly inserted GP elements; `unmatched` applies to Space-Track
and is zero for upsert providers. Duration/outcome refer to the latest finished
attempt; a failure does not overwrite the previous successful record counts.

Unobserved attempt/success timestamps are zero, outcomes/durations/record counts
are NaN, and counters start at zero. Historical provider success times are **not
invented**. Dashboard age queries exclude zero timestamps. Conjunction execution
timestamps/outcomes follow the same convention. A worker outcome describes its
last completed execution, not whether a worker is currently alive.

### Label bounds

- `source`: `canonical`, `celestrak`, `space-track`, `other`; unknown strings map
  to `other` only in metrics, without modifying the actual source argument.
- `provider`: `satcat`, `celestrak`, `space-track`.
- `status`: `fresh`, `aging`, `stale`, `expired`.
- `result`: `received`, `matched`, `imported`, `unmatched`.
- Histogram `le` values are fixed; existing platform `service="api"` is retained.
- No object, NORAD, pair, event, run or chunk-index labels. Pipeline/failure ratios
  are computed in PromQL.

## Prometheus and Grafana

The unchanged Prometheus image scrapes **`api:8000/metrics/`**, job
`orbitalai-api`, every 15 seconds. The existing datasource UID is
`orbitalai-prometheus`; neither container version changes.

The file provider in `observability/grafana/provisioning/dashboards/operations.yml`
loads `json/orbital-operations-overview.json` into folder **OrbitalAI**:

**OrbitalAI - Orbital Operations Overview**, UID `orbitalai-operations`, 16 panels,
30-second refresh, existing theme. Panels cover status, eligibility, duration,
events, failures, chunks, catalog coverage, ephemeris ages, pipeline reduction,
merged events, maximum chunk workloads, ratios, performance, execution counts and
provider outcomes/records. No manual JSON import is needed.

## Limits

- Cache values can be stale; availability and refresh timestamps expose this.
  The latest completed screening may describe a historical target window, while
  catalog eligibility always describes refresh time.
- Operational state is designed for the existing single-host shared filesystem,
  with a common writer UID/permissions. It is not a distributed job ledger.
- Process termination/OOM and telemetry write failures can prevent recording an
  outcome. A started attempt can therefore lack a completion. Existing DB runs
  remain authoritative for successful persisted screening results.
- CLI argument errors before real work and failures in CLI reporting are part of
  entrypoint observation; service-only duration excludes fetch/reporting. No
  scheduler, retry policy, scrape-side provider calls or retrospective provider
  history is added.
- Histogram/rate panels require enough observations; sparse executions can yield
  no p95 or fractional Prometheus `increase()` estimates.
- There is no covariance/Pc or AI orbital mechanics. **Loki and Alertmanager are
  deferred** to later steps; this change stops at Step 6A.
